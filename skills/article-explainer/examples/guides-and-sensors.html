Reading notes for “Harness Engineering”, devCon, 8 October

A harness isa control system.

Birgitta Böckeler's article reduces harness engineering to two questions. Does a control act before the agent does, or after? And is it run by code, or judged by a model? Scroll to build her model one piece at a time. Each step is one click of the slide it could become.

Click 1 of 8

The model

At the centre is a model. It predicts the next token. It has no memory or tools, and it knows nothing about your codebase.

Click 2 of 8

The builder harness

The coding CLI wraps the model in a system prompt, a loop, tools and code search. Anthropic, OpenAI and the Pi authors build this part. You use it, but you don't own it.

Click 3 of 8

Your harness

Then there's everything you add for your own codebase. Böckeler calls it the outer harness, and its job is to get the first attempt right more often and to fix mistakes before a person has to look.

Agent = Model + HarnessLangChain, quoted by Böckeler

“Harness” has no single definition. In this talk, it means this outer ring.

Click 4 of 8

Guides act before

A guide shapes what the agent does before it acts. AGENTS.md, skills, type information and codemods all make a good first attempt more likely.

Click 5 of 8

Sensors check after

A sensor checks what the agent did and feeds the result back, so it can correct itself. Sensors work best when they're written for the model: a lint message that says how to fix the problem is

“a positive kind of prompt injection.”Böckeler

You need both. With sensors alone, the same mistake gets caught every time and made every time. With guides alone, you never find out whether your rules worked.

Click 6 of 8

Code or a model

Every guide and sensor is run by one of two things.

Code (her word: computational) is fast and cheap, and gives the same answer every time. Tests, linters and type checkers are code. They're drawn as solid lines.

A model (inferential) is slower and costs more. It can be wrong, but it understands meaning. AGENTS.md and review agents are models at work. They're drawn as dashed lines.

Click 7 of 8

Your show of hands, on the map

Ask the room who has written an AGENTS.md, a skill, a hook and an extension.

Steps 1 and 2 are dashed: you're asking nicely. Step 3, a hook, runs a real check. Step 4, an extension, reaches inside the builder harness and changes the loop itself.

Each step up the ladder swaps asking for checking.

Click 8 of 8

You steer the harness

Your job is the outermost loop. When the same mistake happens twice, don't fix the code. Add the guide or sensor that would have prevented it.

“Whenever an issue happens multiple times, the feedforward and feedback controls should be improved.”Böckeler

Each time round the loop makes the mistake less likely. That's what trust means here.

Where the checks run

Keep quality left

The sooner a check runs, the cheaper the fix. Cheap code checks run inside the agent's own loop on every change. Model checks cost more, so they run later. The last stop never finishes.

What a harness can and can't catch

Behaviour is still the hard part

Böckeler checked her catalogue of common agent failures against these controls. Code catches structural problems. A model catches some problems of meaning. The most damaging failures still get past both.

Code catches these, reliably

  • Duplicate code
  • Cyclomatic complexity
  • Missing coverage
  • Architectural drift
  • Style violations

A model catches some, at a cost

  • Code that does the same thing a different way
  • Redundant tests
  • Brute-force fixes
  • Over-engineering

Nothing catches these reliably

  • Misdiagnosed problems
  • Features nobody asked for
  • Misunderstood instructions

“Correctness is outside any sensor's remit if the human didn't clearly specify what they wanted in the first place.”Böckeler, on the behaviour harness, which she calls “the elephant in the room”

In the talk

This sets up the Verify end to end slide. She names behaviour as the open problem, and you argue that end-to-end tests are now cheap enough to tackle it. That's where your one line of evolutionary code belongs: code has to survive the real world, and behaviour sensors are that test.

Why every team builds its own

The harness is most needed where it's hardest to build

Three ideas from the end of the article support your domain-specific harness slide.

Harnessability

Some code is easier to harness

Strong types give you a free sensor. Clear module boundaries let you write structural rules. Legacy code has neither, which is why you start from one module.

The implicit harness

You were the harness

Developers bring conventions, “aesthetic disgust at a 300-line function” and a name on the commit. The agent has none of that. A harness writes that knowledge down, but only some of it fits.

Harness templates

A standard one may come

Service templates may grow into harness templates, one per stack. They'll drift from upstream just like service templates do. Don't wait for one.

“A good harness should not necessarily aim to fully eliminate human input, but to direct it to where our input is most important.”Böckeler
